3. Next steps for mode "{{ $mode }}"
{{- if eq $mode "launchpad" }}
   a. Open https://launchpad.obol.org with operator wallet {{ .Values.charon.operatorAddress | default "<charon.operatorAddress>" }}.
   b. Create the cluster or accept the invite, paste THIS node's ENR (step 1) and sign. The chart never signs.
   c. The sidecar polls {{ .Values.charon.dkgSidecar.apiEndpoint }} until every operator has signed{{ with .Values.charon.dkgSidecar.targetConfigHash }} definition {{ . }}{{ end }},
      then the DKG runs automatically. All operators' pods must be up at the same time for the DKG.
{{- else if eq $mode "definition" }}
   a. Make sure this node's ENR (step 1) is one of the operators in the cluster definition
      {{- if .Values.dkg.definition.configHash }} {{ .Values.dkg.definition.configHash }}{{ else if .Values.dkg.definition.url }} at {{ .Values.dkg.definition.url }}{{ else }} in ConfigMap {{ .Values.dkg.definition.configMap }}{{ end }}.
   b. Operators listed with an address must sign it on the Launchpad; ENR-only definitions need no signatures.
   c. Once ready, the DKG runs automatically. All operators' pods must be up at the same time.
{{- else if eq $mode "lock" }}
   The cluster-lock comes from ConfigMap {{ .Values.configMaps.clusterLock }}; no DKG runs.
   {{- if .Values.validatorClient.keystores.secretName }}
   Validator key shares come from Secret {{ .Values.validatorClient.keystores.secretName }}.
   {{- else }}
   WARNING: validatorClient.keystores.secretName is not set; the VC import expects key shares in /charon-data/validator_keys.
   {{- end }}
   The ENR secret must hold the identity that appears in the lock, or charon will not start.
{{- else if eq $mode "lockHash" }}
   The sidecar fetches cluster-lock {{ .Values.charon.lockHash }} from the Obol API; no DKG runs.
   Validator key shares must come from validatorClient.keystores.secretName (currently: {{ .Values.validatorClient.keystores.secretName | default "unset" }}).
{{- end }}
